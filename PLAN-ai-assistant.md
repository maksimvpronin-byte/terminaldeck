# План: ИИ-помощник для диагностики Linux по SSH

> **Статус: первая реализация в ветке `codex/ai-assistant`.**
> Владелец явно разрешил начало разработки 5 сентября 2026 года.
> Коммиты и push — только в эту ветку. Релизы, теги и слияние в `main` не разрешены.
>
> Дата создания: 5 сентября 2026 года.

## 1. Цель и согласованный сценарий

Добавить в TerminalDeck облачного ИИ-помощника, который анализирует состояние
Linux-машины через SSH и объясняет администратору, что происходит и где есть проблемы.

Согласовано в обсуждении:

1. Администратор подключает облачную ИИ в настройках TerminalDeck.
2. У SSH-сессии есть возможность открыть окно ИИ-помощника.
3. Администратор нажимает «Анализ»: помощник готовит и показывает порядок проверок,
   но не выполняет команды на сервере.
4. Перед каждой командой администратор видит точную команду, хост, цель,
   причину проверки, ожидаемую длительность, требуемые права и возможную нагрузку.
5. Администратор отдельно выбирает «Выполнить», «Пропустить» или «Остановить анализ».
6. После выполнения видны stdout, stderr, код завершения/сигнал и длительность.
   ИИ объясняет результат и предлагает следующую команду.
7. Помощник последовательно проверяет ЦПУ, ОЗУ, диски и сервисы. Уточнения,
   включая чтение логов подозрительного сервиса, также требуют отдельных подтверждений.
   Изменение порядка проверок сопровождается объяснением.
8. Администратор получает отчёт с доказательствами, рекомендациями и перечнем
   пропущенных или недоступных проверок.

**Согласовано: каждый запуск каждой диагностической команды подтверждается вручную.**
Для первой версии согласовано последовательное выполнение: следующая команда
не запускается до завершения предыдущей и отдельного подтверждения администратора.
Это заменяет первоначальное предложение об автоматическом и параллельном запуске.
Правило распространяется также на определение ОС, поиск утилит, повторы и резервные проверки.

Согласованные правила подтверждения подробно зафиксированы в разделе 6.1.
Остальные технические решения ниже являются **предложениями для согласования**,
если явно не отмечено обратное. Открытые вопросы перечислены в разделе 12.

## 2. Предлагаемые границы первой версии

- Один анализ одной Linux-машины через активное SSH-подключение.
- Запуск пользователем по кнопке, без фонового расписания и самостоятельного мониторинга.
- Только диагностика и рекомендации: без перезапусков, установки пакетов,
  изменения конфигурации, удаления файлов и исполнения предложенного исправления.
- Без автоматического повышения привилегий. Недостаток прав отражается в отчёте.
- Без массового анализа хостов, RDP-диагностики и произвольного чата с исполнением команд.
- Один выбранный облачный провайдер для первого рабочего варианта;
  архитектура допускает добавление других без изменения SSH-исполнителя.

Последующий диалог по отчёту, история анализов, экспорт, несколько провайдеров
и подтверждаемые исправления рассматриваются отдельно, после первого сценария.

## 3. Пользовательский интерфейс

### Настройки ИИ

- Раздел «ИИ-помощник»: провайдер, модель, API-ключ и «Проверить подключение».
- Наличие сохранённого ключа отображается без раскрытия его значения.
- Явное объяснение: показатели и выбранные фрагменты журналов передаются
  настроенному облачному провайдеру. SSH-пароли и приватные ключи не передаются.
- Проверка подключения не собирает данные с сервера; возможный оплачиваемый
  тестовый запрос должен быть понятен пользователю.
- Формат произвольного API endpoint и поддержка совместимых API ещё не согласованы.

### Окно помощника

- Точка входа рядом с управлением SSH-сессией.
- Постоянно видны имя хоста и адрес. Запущенный анализ привязан к конкретному
  подключению и не переключается на другой хост при смене активной вкладки.
- До настройки провайдера отображается понятный переход в настройки.
- «Анализ» готовит план без исполнения команд на сервере; «Остановить» отменяет анализ.
- Видны последовательность проверок и карточка следующей команды с отдельным
  подтверждением. Нет кнопок «Разрешить всё» или постоянного разрешения на команды.
- История показывает состояния: предложено → ожидает подтверждения → подтверждено →
  выполняется → завершено / ошибка / отменено. Пропуск отмечается отдельно.
- Ход работы показывается этапами и счётчиком проверок. Процент готовности
  не имитируется, если количество уточнений заранее неизвестно.
- Доступен раскрываемый список проверок: назначение, команда, статус,
  длительность, вывод и ограничения результата.
- Терминал остаётся доступен админу; команды диагностики не печатаются в его shell.
- Повторный запуск не смешивает результаты разных анализов.
- Интерфейс и сообщения доступны на русском и английском.

Формат размещения — боковая панель или отдельное окно — предстоит выбрать.

## 4. Процесс анализа

### 4.1. Подготовка

Проверить активность подключения, доступность настройки ИИ и состояние хранилища.
Присвоить анализу идентификатор и зафиксировать подключение, время начала и бюджет.
Проверки локального состояния не должны незаметно выполнять удалённые команды.
Определение ОС, доступных утилит и менеджера сервисов предложить как первые команды
с отдельным подтверждением каждой. Наличие systemd, journalctl или дополнительных
пакетов не предполагается заранее.

### 4.2. Базовые проверки

| Область | Какие данные нужны | Как интерпретировать |
| --- | --- | --- |
| ЦПУ | Число ядер, load average, несколько измерений CPU, iowait, наиболее активные процессы | Load average не равен проценту CPU; учитывать ядра и ожидание I/O |
| ОЗУ | Доступная память, кеш, swap, активность swap, процессы-потребители | Занятая кешем память и сам факт использования swap не доказывают проблему |
| Диски | Заполнение файловых систем и inode, точки монтирования, доступные признаки ошибок I/O | Учитывать тип файловой системы; не считать все виртуальные разделы проблемными |
| Сервисы | Неисправные службы, состояние подозрительных сервисов, доступные сведения о перезапусках | Отличать ожидаемо остановленный сервис от сбоя |
| Системные события | Доступные сообщения OOM, ошибок дисков и других сбоев за ограниченный период | Указывать время события и не выдавать старый сбой за текущий |

Использовать короткую серию измерений, где один снимок не позволяет сделать вывод.
Не запускать нагрузочные тесты, полные обходы файловой системы и не устанавливать
утилиты автоматически. Недоступная проверка не должна останавливать остальные.

### 4.3. Уточнения по результатам

Модель получает результаты базовых проверок и выбирает дополнительные действия
из разрешённых диагностических инструментов. Каждое уточнение имеет основание:
какой результат вызвал подозрение и что следующая проверка должна выяснить.
Выбор модели только создаёт предложение: исполнение ожидает отдельного ручного
подтверждения. Пропущенная проверка не запускается обходным способом; если от неё
зависит уточнение, помощник объясняет ограничение или предлагает другую команду.

Примеры:

- Недостаток памяти → основные потребители → связь процесса с сервисом →
  доступные записи OOM и журнал сервиса.
- Упавшая служба → сведения о завершении → журнал вокруг времени сбоя →
  проверка выявленной зависимости, если она доступна разрешёнными инструментами.
- Почти заполненный раздел → ограниченная проверка источников заполнения →
  связанные сообщения сервиса об ошибках записи.

Читать только ограниченные фрагменты логов с временными метками и указанием источника.
Не отправлять все журналы машины «на всякий случай». Не считать процесс сервисом
без подтверждения связи: он может принадлежать контейнеру или пользовательскому запуску.

### 4.4. Завершение

Остановиться, когда собраны достаточные данные, исчерпан бюджет, пользователь
нажал «Остановить» или потеряно подключение. После остановки не начинать новые
команды и запросы модели; уже отправленные облачному провайдеру данные отозвать нельзя.

При ошибке провайдера сохранить доступные результаты проверок в текущем окне
и явно сообщить, что ИИ-интерпретация не завершена. Частичный анализ не выглядит успешным.

## 5. Формат отчёта

1. **Контекст:** хост, время, длительность и полнота анализа.
2. **Общая оценка:** обнаруженные проблемы либо отсутствие признаков проблем
   в проверенном интервале. Это не гарантия полной исправности машины.
3. **Ресурсы:** фактические показатели ЦПУ, памяти и дисков.
4. **Проблемы:** серьёзность, наблюдаемый факт, вероятная причина и последствия.
5. **Доказательства:** ссылки на конкретную проверку и строки/фрагменты результата.
6. **Рекомендации:** приоритет и цель действия; рекомендации не исполняются автоматически.
7. **Ограничения:** недоступные журналы, недостаток прав, обрезанные данные,
   таймауты, пропуски по решению администратора и то, что требует дальнейшей проверки.

Разделять наблюдение, гипотезу и рекомендацию. Не придумывать показатели,
логи и уверенность в процентах. Ссылка на доказательство должна вести к реально
полученному результату этого анализа. Текст модели отображается как недоверенный контент.

## 6. Исполнение и ограничения

### 6.1. Ручное подтверждение каждой команды — согласованное требование

- Подтверждение относится к одному запуску точной показанной команды на указанном
  активном SSH-подключении. Оно не разрешает весь этап, инструмент или анализ целиком.
- Повтор после ошибки/таймаута, изменение параметров, новая команда и резервный
  вариант при отсутствии утилиты требуют нового подтверждения.
- Нельзя объединять несколько проверок через `;`, `&&`, скрытый скрипт или иной
  составной запуск ради обхода отдельных подтверждений. Если инструменту нужны
  несколько команд, каждая отображается и подтверждается отдельно.
- Пользователь видит всю исполняемую команду и аргументы до подтверждения;
  подмена команды после подтверждения недопустима.
- Подтверждение не должно сохраняться для другого подключения, повторного анализа
  или переживать остановку/блокировку. После переподключения требуется новое предложение.
- Пропуск не считается успешной проверкой. ИИ объясняет, как он влияет на выводы.
- История порядка, подтверждений, запусков и результатов доступна в окне анализа.
- Следующая команда ожидает завершения предыдущей и собственного подтверждения.

Предлагаемая реализация: main process хранит неизменяемое предложение с идентификатором
анализа, подключения, команды и параметрами. Подтверждение потребляется однократно;
повторный клик, повтор IPC-сообщения или поздний ответ не запускает команду заново.
Сама модель не может подтвердить созданное ею предложение.

### 6.2. Каталог и исполнитель

Предлагается каталог диагностических инструментов со структурированными параметрами,
а не право модели выполнять произвольную строку shell. TerminalDeck самостоятельно
проверяет название инструмента, параметры, выбранное подключение и бюджет.

- Проверки в каталоге должны быть ограничены по стоимости и не менять конфигурацию.
- Имена сервисов, пути и прочие значения из вывода сервера валидируются;
  их нельзя напрямую подставлять в shell-команды.
- Команда выполняется через отдельный SSH exec-канал существующего подключения.
- Исполнитель возвращает stdout, stderr, код завершения или сигнал, время,
  признак таймаута/отмены и признак обрезанного вывода.
- Бюджеты ограничиваются в main process и действуют независимо от указаний модели.
- Учитывается время открытия канала, а не только ожидание вывода после открытия.
- Закрытие SSH-канала не считается доказательством завершения всех удалённых процессов;
  диагностика должна состоять из ограниченных по времени операций, без фоновых запусков.

Начальные значения **для обсуждения и последующей проверки**, не утверждённые требования:

| Ограничение | Предложение |
| --- | --- |
| Одновременные команды одного анализа | 1 — согласованное последовательное выполнение |
| Время одной проверки | До 15 секунд, отдельные исключения внутри каталога |
| Бюджет активной работы анализа | В первой реализации: 5 минут на SSH/API, без ожидания ручных подтверждений |
| Число дополнительных проверок | До 10 |
| Число обращений к модели | В первой реализации: до 24, включая итоговый отчёт; интерпретация после каждой выполненной команды |
| Суммарный stdout + stderr одной проверки | До 64 КиБ |
| Суммарный сбор данных за анализ | До 512 КиБ до фильтрации |

Отдельно ограничить суммарные входные и выходные токены всех запросов: повторная
передача контекста тоже расходует бюджет. Конкретные значения зависят от выбранной модели.
Повторные запросы при временных ошибках провайдера также входят в общий бюджет
и не разрешают повторное исполнение SSH-команды. Ожидание решения администратора
показывается отдельно и не расходует бюджет активной работы. После долгой паузы
ИИ отмечает устаревание измерений; обновление данных требует нового подтверждения.

## 7. Данные и безопасность

- API-ключ хранится через существующее зашифрованное хранилище; renderer
  получает статус настройки, а не сохранённый ключ. Запросы к провайдеру идут из main process.
- Передавать минимально нужный контекст, исключая SSH-пароли, приватные ключи,
  содержимое хранилища и произвольную историю терминала.
- Перед отправкой фильтровать распространённые форматы токенов, паролей и ключей.
  Фильтрация снижает риск, но не гарантирует удаления всех секретов из произвольного лога.
- Вывод команд, имена файлов и логи — недоверенные данные. Инструкции внутри них
  не могут разрешать команды, менять хост, отключать ограничения или запрашивать секреты.
- Разрешение на диагноз не означает разрешения на отправку данных сторонним адресатам,
  выбранным моделью или текстом журнала. Используется только настроенный провайдер.
- По умолчанию предлагается хранить результаты только в памяти текущей сессии.
  Постоянная история и экспорт требуют отдельного решения о защите и сроках хранения.
- Блокировка хранилища должна прекращать новые действия анализа и скрывать отчёт;
  точное поведение уже выполняющихся операций требуется согласовать и проверить.
- При переподключении создаётся новая привязка; старый анализ не продолжает работу
  на новом подключении автоматически, даже если имя хоста совпадает.

## 8. Предлагаемая техническая структура

Точки интеграции в текущем проекте:

- `src/main/ssh/SSHManager.ts`: существующий `exec()` открывает отдельный канал,
  возвращает только stdout и отбрасывает stderr. Для диагностики нужен отдельный
  метод с полным результатом либо совместимое расширение без поломки текущих потребителей.
- `src/main/vault/`: хранение API-ключа с учётом блокировки и смены мастер-пароля.
- `src/main/ipc/`, `src/preload/`, `src/shared/`: типизированные команды запуска,
  подтверждения конкретной команды, пропуска, отмены, настройки и события прогресса.
  Валидация входных данных и одноразовых подтверждений в main process.
- `src/renderer/src/components/` и `state/`: настройки, окно помощника и состояние анализа.

Предлагаемые отдельные обязанности:

| Компонент | Ответственность |
| --- | --- |
| Адаптер провайдера | Авторизация, запросы модели, нормализация ответов, usage и ошибок |
| Координатор анализа | Порядок, ожидание подтверждений, связь с подключением, бюджеты, отмена и завершение |
| Каталог диагностики | Разрешённые проверки, параметры, совместимость с ОС |
| SSH-исполнитель | Ограниченное исполнение и полный результат команды |
| Подготовка данных | Фильтрация, обрезка и маркировка происхождения результатов |
| Формирование отчёта | Проверка структуры и ссылок на доказательства |
| Интерфейс | Настройки, прогресс, просмотр результатов и отчёт |

Модель не получает прямого доступа к IPC, хранилищу или карте SSH-подключений.
Окончательные имена модулей и контрактов определить перед реализацией.

## 9. Этапы реализации после разрешения

1. **Согласовать требования.** Закрыть вопросы первой версии из раздела 12;
   проверить документацию выбранного API и актуальные условия работы с данными.
2. **Спроектировать контракты и интерфейс.** Состояния анализа, формат результатов,
   инструменты, бюджеты, макет настроек и окна помощника.
3. **Сделать диагностический исполнитель.** Полный результат команды, каталог,
   таймауты, лимиты и отмена; проверить на тестовой Linux-машине без модели.
4. **Подключить облачного провайдера.** Хранение ключа, проверка соединения,
   фильтрация данных и контролируемые запросы.
5. **Реализовать цикл анализа.** План → предложение команды → ручное подтверждение
   или пропуск → результат → следующее предложение/уточнение → отчёт.
6. **Подключить интерфейс.** Прогресс, остановка, доказательства, ошибки,
   локализация и поведение при блокировке/переподключении.
7. **Проверить весь сценарий.** Контролируемые неисправности на тестовых машинах,
   качество рекомендаций, стоимость, длительность и отсутствие регрессий SSH/SFTP.

Каждый этап начинается только в рамках отдельно разрешённой разработки.
Текущее разрешение включает реализацию первой версии и отправку изменений в отдельную ветку.

## 10. Проверки и критерии готовности

- Настройка провайдера, запуск анализа и получение отчёта доступны из интерфейса.
- Нажатие «Анализ» не выполняет ни одной удалённой команды до ручного подтверждения.
- Для каждой команды показаны порядок, точный текст, хост, цель, причина,
  длительность, права и возможная нагрузка; после запуска доступны результаты.
- Нет автозапуска базовых проверок, уточнений, повторов и резервных команд.
- Одно подтверждение вызывает не более одного запуска. Проверены двойной клик,
  повтор IPC, подмена параметров, позднее подтверждение после отмены/блокировки
  и переподключение к другому либо тому же хосту.
- Следующая команда не стартует параллельно или без нового подтверждения.
- Проверены пропуск обязательного для уточнения шага, изменение порядка с объяснением,
  длительное ожидание решения и отчёт по частичным/устаревшим данным.
- CPU, память, диски и сервисы представлены результатами или явным объяснением,
  почему проверка недоступна.
- Подозрительный сервис приводит к обоснованному запросу его состояния/логов;
  отсутствие подозрений не вызывает бессистемное чтение журналов.
- Основной терминал остаётся работоспособным, включая ввод и поток вывода.
- Остановка, обрыв SSH, закрытие сессии и блокировка не оставляют бесконтрольный цикл.
- Проверены отсутствующие утилиты/systemd, отказ в доступе к журналу, большие выводы,
  stderr, ненулевой код, зависание открытия канала и завершение по сигналу.
- Проверены неверный API-ключ, недоступность провайдера, ограничение запросов,
  некорректный ответ модели и исчерпание бюджета.
- Модель не может выполнить неизвестный инструмент, произвольную команду,
  подменить подключение или превратить данные журнала в инструкцию.
- Подстановка вредоносных имён сервисов и путей не приводит к исполнению shell-кода.
- Отчёт различает факты и гипотезы; доказательства существуют и относятся к этому анализу.
- API-ключ и тестовые секреты не появляются в renderer, диагностических логах
  и отправляемом модели контексте; ограничения фильтрации задокументированы.
- Проверены исправный сервер, кратковременная нагрузка, нехватка памяти,
  заполнение места/inode и сбой сервиса. Контролируемые сбои создаются только
  в специально выделенной тестовой среде.
- Проверены русский/английский интерфейс, клавиатурная навигация и минимальный размер окна.
- TypeScript, lint, профильные тесты и сборка проходят; UI и интеграционный сценарий
  проверены отдельно от модульных тестов.

## 11. Риски и ограничения продукта

- Короткий анализ не заменяет мониторинг и не доказывает отсутствие редких проблем.
- Одинаковые показатели требуют разной интерпретации для БД, файлового сервера,
  контейнерного хоста и обычной виртуальной машины.
- Успешное выполнение команды не гарантирует правильность интерпретации модели.
- Облачная диагностика зависит от сети, лимитов провайдера и доступного бюджета.
- Журналы могут содержать персональные и служебные данные даже после фильтрации секретов.
- Чтение тоже потребляет ресурсы; тяжёлые диагностические операции требуют ограничений.
- Поведение отмены и блокировки необходимо проверять на всей цепочке UI → main → SSH/API.

## 13. Первая реализация и границы проверки

Реализованы:

- Настройки адреса, модели, API-ключа и согласия на передачу данных; проверка API
  небольшим запросом без данных сервера. Настройки и ключ зашифрованы в vault.
- Каталог из 14 базовых проверок и дополнительных инструментов. Отдельного
  подтверждения требует даже первая команда `cat /etc/os-release`.
- CPU, память, процессы; по дискам — структура устройств, место/inode, mount options,
  задержки/очереди I/O, ошибки ядра и software RAID. Уточнения: SMART, NVMe,
  LVM thin pools, ZFS, I/O процессов, размер журнала, открытые удалённые файлы,
  ограниченный `du`, состояние и журнал конкретного сервиса.
- Одноразовые подтверждения в main process, последовательное исполнение, пропуск,
  раннее завершение с отчётом по собранным данным и отмена.
- Интерпретация моделью после выполненной команды; следующая команда остаётся
  предложением. Изменения порядка отражаются в видимой последовательности.
- История результатов, структурированный отчёт, ссылки на реальные результаты
  и явные ограничения пропущенных/неуспешных проверок.
- Отмена по блокировке, отключению SSH, перезагрузке/закрытию окна и изменению настроек ИИ.
- Русский и английский интерфейс; результаты остаются в памяти текущей SSH-сессии.

Технические ограничения первой реализации:

- Требуется Chat Completions API с `max_completion_tokens` и текстовым JSON-ответом;
  Responses-only API и специфические схемы авторизации других провайдеров не поддержаны.
- HTTPS обязателен, кроме HTTP на loopback для локальных совместимых серверов.
  Перенаправления API не выполняются. При смене адреса сохранённый ключ не переносится.
- 15 секунд и 64 КиБ объединённого вывода на команду, 512 КиБ собранных данных,
  24 запроса модели и 5 минут активной работы. Между подтверждениями время не расходуется.
- Контекст адаптивно ограничивается по байтам; модель получает помеченные выдержки
  начала и конца вывода. Ограничен суммарный объём повторных запросов и резервов ответов.
- Нет автоматического sudo, установки утилит, исправлений, повторов SSH-команд,
  SMART-самотестов, scrub, `fsck`, `badblocks` и бенчмарков.
- Фильтрация секретов эвристическая; произвольные логи могут содержать чувствительные данные.
- Постоянной истории и экспорта отчётов нет; настройки ИИ не включены в переносимый
  backup конфигурации. Провайдер на другой машине настраивается отдельно.
- Автоматически проверены модульные сценарии, реальный локальный SSH-транспорт с
  фиксированными ответами и локальный API, совместимый по формату. Интерфейс проверен
  в Electron при 1280×800 и 900×560. Проверка настоящей облачной модели и диагностика
  реальных Linux-серверов остаются отдельным приёмочным этапом с ключом администратора.
