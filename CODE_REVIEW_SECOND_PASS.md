# Повторный анализ кода TerminalDeck и план работ

Дата: 15 сентября 2026 года. Версия приложения: **0.18.0**. Проверенный commit: **dce46e8**.

Исходный код, настройки и рабочие данные приложения не изменялись. Создан только этот отчёт. Предыдущий анализ сохранён в [CODE_REVIEW_PLAN.md](CODE_REVIEW_PLAN.md).

## 1. Главный вывод

После первого обзора исправлены существенные проблемы с путями Windows, состоянием vault, запросами аутентификации, записью JSON и завершением соединений. Однако часть исправлений закрывает только отдельные этапы операции: ошибки остаются между чтением и сохранением, между началом подключения и регистрацией ресурса, между проверкой разрешения и фактической передачей данных.

**Первоочередная работа — сохранность секретов и файлов, полноценная отмена соединений и обработка ошибок потоков.** Затем нужно устранить гонки синхронизации и открытия туннелей, сохранить сообщения об ошибках передачи и определить границы обмена буфером RDP.

## 2. Объём и метод проверки

Повторно рассмотрены основные подсистемы:

- Electron: запуск, окно, sandbox, навигация, IPC, завершение ресурсов, обновления.

## 4. Подтверждённые проблемы

Приоритеты: **P1** — исправить в первую очередь из-за риска потери данных, незавершённого подключения или необработанного исключения main. **P2** — следующий этап: согласованность состояния, управление ресурсами и видимость результата операции.

### R1. P1 — повторный unlock теряет секрет, сохранённый во время derivation

**Подтверждено изолированным воспроизведением.**

Источники: [Vault.ts](src/main/vault/Vault.ts), строки 104–122 и 266–276; [App.tsx](src/renderer/src/App.tsx), обработчик `UnlockScreen.submit`.

Последовательность:

1. Vault уже открыт, запускается ещё один `unlock`.
2. `unlock` читает `vault.json` и ждёт `deriveKey`.
3. `setSecret` записывает новый секрет в текущий vault.
4. Завершившийся `unlock` вызывает `adopt(file, key)` со старым снимком.
5. Секрет исчезает из памяти. Следующий `setSecret` записывает старый набор секретов на диск, окончательно теряя запись.

Очередь охватывает асинхронные операции с мастер-паролем, но `setSecrets` работает вне неё. Счётчик `generation` меняется при lock и не обнаруживает обычную запись секрета. Экран разблокировки допускает повторный submit без состояния busy, поэтому несколько запросов могут уже стоять в очереди, когда первый открыл интерфейс.

**План:** сделать повторный unlock безопасным для уже открытого vault; проверять версию прочитанного состояния перед его публикацией. Запретить повторный submit в UI как дополнительную меру. Защита в main обязательна.

**Критерий готовности:** секрет, сохранённый во время второго unlock, доступен сразу, после последующих записей и после lock/unlock.

### R2. P1 — неудачное сохранение профиля может уже изменить или удалить его пароль

**Подтверждено изолированным воспроизведением обработчика IPC.**

Источники: [ipc/store.ts](src/main/ipc/store.ts), строки 28–32, 51–60, 105–107; [ipc/secrets.ts](src/main/ipc/secrets.ts), строки 30–54.

Обработчик сначала вызывает `applySecret`, затем сохраняет профиль. Если пользователь выбрал забыть пароль, `applySecret` удаляет секрет из vault до записи `sessions.json`. При ошибке второй записи профиль остаётся прежним и продолжает ссылаться на уже удалённый секрет.

При замене пароля аналогично возможно частично применённое изменение: интерфейс сообщает об ошибке сохранения, но пароль уже заменён. Последовательная запись обычного и gateway-пароля создаёт ещё одну точку частичного успеха.

**План:** оформить сохранение профиля вместе с секретами как одну операцию с подготовкой изменений и откатом. Распространить правило на credentials, groups, inventory overrides и Git-folder overrides. Обработку удаления и отвязки Git-папки включить в ту же проверку согласованности.

**Критерий готовности:** искусственный отказ каждой записи оставляет либо полностью старый, либо полностью новый профиль с соответствующими секретами; результат однозначно сообщается UI.

### R3. P1 — fallback SFTP всё ещё повреждает оригинальный файл при обрыве

**Подтверждено изолированным воспроизведением `writeRemoteFile`.**

Источник: [SFTPManager.ts](src/main/ssh/SFTPManager.ts), строки 357–408.

Если сервер не предлагает `posix-rename` либо не удаётся сохранить владельца/права временного файла, код:

1. Загружает полную новую копию во временный файл.
2. Удаляет временный файл.
3. Повторно загружает данные прямо в исходный путь.

Обрыв на третьем шаге оставляет усечённый оригинал. Для symlink используется непосредственная запись без временного файла. Сохранение владельца и самой ссылки — осмысленные ограничения, однако текущий fallback не обеспечивает сохранность содержимого и выполняется без отдельного сообщения о смене режима записи.

**План:** определить безопасное поведение при невозможности замены через rename. Не переключать защищённую операцию молча на разрушительную запись; возвращать понятную ошибку или явно выбранный пользователем режим с описанными ограничениями. Отдельно определить семантику symlink и сохранения метаданных.

**Критерий готовности:** сбой на любом этапе защищённого режима оставляет прежний файл целым; проверены сервер без расширения, отказ `chown`, отказ `chmod`, обрыв и symlink.

### R4. P1 — отмена SSH не завершает ожидание `forwardOut` и открытия shell

**Ожидание `forwardOut` подтверждено изолированным воспроизведением. Для `shell` установлен такой же пробел в коде.**

Источник: [SSHManager.ts](src/main/ssh/SSHManager.ts), строки 494–505, 643–646, 699–746, 750–760.

После успешной аутентификации обработчик отмены `signIn` снят. Следующий `forwardOut` ждёт callback без своего AbortSignal и срока ожидания. Если bastion остаётся подключённым, но не отвечает на запрос канала, `cancelConnect` только меняет состояние сигнала.

В воспроизведении после `cancelConnect` и `releaseAll` Promise оставался незавершённым, а аутентифицированный bastion не был закрыт. Клиенты передаются в `attempt.opened` только после завершения всей цепочки. `openShell` также ждёт callback без отмены; проверка сигнала после `await run` не может прервать само ожидание.

**План:** регистрировать каждый клиент при создании, закрывать его непосредственно по отмене, ограничить ожидание forwarding/shell и корректно обрабатывать поздние callback. Продлить владение попыткой на автоматическое открытие туннелей в IPC.

**Критерий готовности:** закрытие панели или renderer на любой стадии подключения быстро завершает Promise и закрывает все созданные ресурсы даже при полном отсутствии ответа сервера.

### R5. P1 — ошибки потоков RDP и SSH-лога остаются необработанными

**Подтверждены два изолированных сценария.**

Источники: [FreeRdpBridge.ts](src/main/rdp/FreeRdpBridge.ts), строки 226–239 и 473–487; [SSHManager.ts](src/main/ssh/SSHManager.ts), строки 766–771 и 813–815.

**RDP:** проверка `stdin.writable` и `try/catch` вокруг `stdin.write` не перехватывают асинхронное событие `error`. При закрытии принимающей стороны pipe возможен `EPIPE` после успешного входа в `write`. Обработчик `child.on('error')` не заменяет обработчик ошибки `child.stdin`. В воспроизведении событие поймал только специально добавленный наблюдатель проверки.

**SSH:** созданный `logStream` не имеет обработчика `error`. Ошибка открытия или записи лога, например `EACCES` либо `ENOSPC`, становится необработанным событием main. Подтверждено отсутствие слушателя и выброс ошибки при таком событии. Запись также не учитывает `write() === false`, поэтому медленный диск способен накапливать очередь логирования независимо от терминального backpressure.

**План:** назначать обработчики ошибок потоков до первой операции записи. Ошибку RDP направлять в завершение конкретной desktop-сессии; ошибку лога — в отключение логирования с сообщением пользователю. Определить ограничение буфера логирования.

**Критерий готовности:** асинхронный `EPIPE`, недоступный каталог логов и заполнение диска не создают необработанных исключений главного процесса.

### R6. P2 — ошибка Git preview восстанавливает удалённую папку

**Подтверждено изолированным воспроизведением.**

Источник: [GitFolderStore.ts](src/main/gitFolders/GitFolderStore.ts), строки 174–175 и 228–240.

`preview` запоминает объект папки перед ожиданием Git. В `catch` он передаёт этот старый объект в `saveLink`, который вызывает `sessionStore.saveGroup` с семантикой upsert.

Если во время ожидания папка удалена, ошибка Git создаёт её заново. Если папка изменена, старый объект может затереть новые настройки. Проверка актуальности в `apply` не защищает этот путь обработки ошибки.

**План:** перед записью ошибки заново найти папку и проверить поколение запроса и актуальность Git-link. Обновлять только служебные поля текущего объекта. Удаление должно аннулировать и успешный, и ошибочный результат незавершённого preview.

**Критерий готовности:** удалить или изменить папку во время fetch; ни успех, ни ошибка старого запроса не возвращают старое состояние.

### R7. P2 — inventory публикует старые параметры подключения после их сохранения

**Подтверждено изолированным воспроизведением.**

Источники: [InventoryStore.ts](src/main/inventory/InventoryStore.ts), строки 24–29, 135–140, 165–209; [state/slices/inventory.ts](src/renderer/src/state/slices/inventory.ts), строки 51–54.

Корневая группа дерева получает имя и наследуемые параметры из снимка source, с которым началась синхронизация. `stillCurrent` проверяет только repo URL, branch и paths.

Если во время parse изменить username или другие параметры, конфигурация сохраняет новые значения, но дерево публикуется со старыми. Повторный `sync`, вызванный после сохранения, получает уже выполняющийся Promise и не гарантирует новый проход. В проверке source содержал новый username, а опубликованная корневая группа — старый.

**План:** перед публикацией собирать корневую группу из актуального source. При изменении параметров чтения аннулировать старый результат и ставить в очередь синхронизацию последней версии.

**Критерий готовности:** имя, username, port и остальные наследуемые поля в опубликованном дереве соответствуют сохранённому источнику после пересечения save и sync.

### R8. P2 — туннель может открыться после очистки SSH-соединения

**Подтверждено изолированным воспроизведением.**

Источник: [PortForwardManager.ts](src/main/ssh/PortForwardManager.ts), метод `start`, строки 129–203; методы `stop` и `stopAllForConnection`, строки 206–222.

Туннель добавляется в `active` после `await server.listen` или `forwardIn`. До этого `stopAllForConnection` его не видит. Если соединение завершается в промежутке, callback открытия затем регистрирует ресурс уже после очистки.

В проверке остановка до завершения `listen` оставила сервер незакрытым и добавила правило в `listActive` после завершения подключения. Параллельные `start` одного правила также не разделяют запись о незавершённой операции.

**План:** учитывать состояния opening/active/stopping, регистрировать сервер до ожидания и отменять opening вместе с соединением. Отдельно определить, должны ли существующие соединения через туннель закрываться кнопкой Stop: сейчас `server.close()` прекращает новые подключения, но сам по себе не уничтожает уже принятые сокеты.

**Критерий готовности:** поздний callback открытия после Stop или SSH disconnect закрывает ресурс и не возвращает правило в активный список.

### R9. P2 — буфер RDP ограничен фокусом окна, но не выбранной сессией

**Рассылка двум desktop-сессиям подтверждена изолированным воспроизведением. Требуемая политика выбора получателя должна быть определена отдельно.**

Источники: [FreeRdpBridge.ts](src/main/rdp/FreeRdpBridge.ts), строки 346–352, 395–399, 573–585; [td_rdp.c](resources/freerdp/shim/td_rdp.c), обработчики `td_clip_server_format_data_request` и `td_clip_local_request`.

Все готовые RDP-сессии с включённым clipboard в одном сфокусированном окне получают локальный буфер. Выбранная вкладка, видимость desktop и активная панель в решении не участвуют. Это подтверждённое поведение; оно не означает, что каждый пользователь ожидает обмен только с одной сессией.

В обратную сторону достаточно открытого vault: фоновая desktop-сессия может изменить локальный clipboard, даже когда окно приложения потеряло фокус. Нативный клиент также сохраняет ранее объявленные данные и обслуживает запросы файлов самостоятельно; остановка нового polling в main не равнозначна отзыву уже переданного набора файлов.

**План:** явно определить политику: все разрешённые desktop либо активный desktop. Если выбрана изоляция, передавать активный desktop ID в main и проверять его в обоих направлениях. Отдельно решить, какие уже начатые передачи продолжаются после lock и как отзываются будущие запросы к ранее объявленным файлам.

**Критерий готовности:** сценарии с двумя desktop, SSH-вкладкой, потерей фокуса и lock имеют однозначно заданное поведение и проверяются на уровне main и native.

## 5. Дополнительные проблемы, установленные по коду

Эти пункты не выдаются за полноценные воспроизведения через интерфейс приложения.

### R10. P2 — обновление SFTP-списка стирает ошибку передачи

Источники: [useTransfers.ts](src/renderer/src/hooks/useTransfers.ts), строки 68–80; [SftpPanel.tsx](src/renderer/src/components/SftpPanel.tsx), строки 86–93 и 211–246.

После ошибки `runPlan` или сообщения о пропущенных изменившихся путях hook устанавливает `onError`, затем безусловно вызывает `onFinished`. Для upload/relay это запускает `load`. Успешное чтение каталога вызывает `setError(null)` и убирает только что показанную ошибку передачи.

**План:** разделить ошибки списка и итог последней передачи. Обновление каталога не должно подтверждать успех копирования.

**Критерий готовности:** при отказе upload и успешном последующем list сообщение о неудачной передаче остаётся видимым.

### R11. P2 — отсутствующий jump host приводит к неявному изменению маршрута

Источники: [SSHManager.ts](src/main/ssh/SSHManager.ts), строки 423–445; [SessionStore.ts](src/main/store/SessionStore.ts), строки 55–58; [store/hosts.ts](src/main/store/hosts.ts).

Цепочка прекращает построение, если `jumpHostId` не найден. Ошибка не возвращается, и уже собранная часть цепочки выполняется. При удалённом единственном bastion это означает попытку прямого подключения к целевому хосту. Удаление сессии не обрабатывает ссылки на неё как на jump host.

Цикл также лишь обрывает обход через `seen`. Новый общий `findProfile` используется при выборе целевого хоста в IPC, но поиск промежуточного хоста всё ещё ограничен `sessionStore`. Сейчас UI выбора jump host также ограничен сохранёнными сессиями; произвольную поддержку inventory-bastion он не обещает.

**План:** проверить всю цепочку до открытия первого клиента; отсутствующие ссылки и циклы возвращать как ошибку маршрута. Если поддерживаются bastion из inventory/Git-папок, согласованно использовать общий поиск в UI и main.

**Критерий готовности:** удаление bastion и цикл A → B → A не приводят к попытке подключения по другому маршруту.

## 6. Остальные ограничения и направления проверки

### Согласованность backup и Git-folder apply

Rollback импорта охватывает исключения, которые процесс успел обработать. Последовательность изменений нескольких JSON-файлов не имеет журнала восстановления после аварийного завершения процесса между записями. Это ограничение текущей реализации, а не воспроизведённый power-loss тест.

`GitFolderStore.apply` сначала сохраняет дерево, затем удаляет orphaned secrets и обновляет ссылку папки. Ошибка позднего шага оставляет частично применённое состояние. Эти операции нужно включить в план согласованного сохранения R2.

Экспорт backup записывает выбранный файл напрямую. При перезаписи существующего backup стоит использовать временный файл с последующей заменой.

### IPC и структура локальных данных

Проверка sender добавлена и улучшает границу доверия. Проверка содержимого сообщений остаётся выборочной: большинство обработчиков всё ещё полагаются на типы TypeScript. В частности, следует проверить допустимые диапазоны размеров терминала, объёмы payload и идентификаторы ресурсов.

Проверка формы transfer plan не доказывает, что переданные пути принадлежат ранее подготовленному плану для этой сессии. Возможное усиление — хранить план в main под непрозрачным ID и принимать обратно только решения по конфликтам. Обнаруженная цепочка выполнения произвольного кода из внешнего содержимого здесь не утверждается.

`isOwnPage` для production проверяет суффикс пути `/renderer/index.html`; точное сравнение с адресом собственного bundled renderer делает правило точнее. Навигация уже ограничена отдельно, поэтому это мера усиления, а не доказанный обход.

Чтение JSON требует отдельной проверки схемы и версии данных: синтаксически корректный JSON ещё не является корректным store. При восстановлении нужно различать повреждение содержимого и ошибку доступа к файлу.

### Передачи и файловая система

`stillAsPlanned` проверяет наличие и тип назначения, но не сравнивает его содержимое, размер или mtime с тем, что видел пользователь. Изменения существующего файла между preview и записью этим не обнаруживаются.

Защита локального имени закрывает строковые обходы пути. Проверка существующих родительских symlink/junction и гонок замены назначения требует отдельной файловой интеграции. Предсказуемое имя временного файла тоже не заменяет эксклюзивное создание.

План передачи в renderer не хранит неизменяемую привязку к исходному `connectionId`; при reconnect стоит аннулировать открытый диалог конфликтов. Полный сценарий через UI в этом проходе не воспроизводился.

### Длительные операции и ресурсы

Git-команды и очередь inventory worker не имеют общего deadline и пользовательской отмены. Зависшая команда может надолго удержать синхронизацию.

У `SSHManager.exec` timeout начинается внутри callback открытия exec-канала. Само ожидание callback и размер накопленного вывода требуют отдельных границ; это относится и к мониторингу.

Native RDP теперь получает stop непосредственно в reader thread и вызывает abort подключения. Main завершает stdin, но не имеет ограниченного по времени принудительного завершения зависшего дочернего процесса. Нужен интеграционный сценарий, в котором native перестаёт обрабатывать команды.

### Структура кода

Разделение main / preload / renderer соответствует задачам проекта. Worker для inventory, виртуализация файловых строк, подтверждения обработки SSH-вывода и RDP-кадров дают полезную основу для ограничения нагрузки.

Новый `useTransfers` уменьшил связанность файловой панели, а общий поиск хостов убрал часть дублирования. Крупными остаются `Sidebar`, `RemoteScreen`, `SSHManager` и `SftpPanel` — примерно по тысяче строк с комментариями. Делить их следует вокруг конкретных обязанностей: владение ресурсами, аутентификация, публикация результата передачи, ввод и отображение desktop.

Главная потребность — единые правила завершения и сохранения операций. Само уменьшение размера файлов не исправит описанные гонки.

## 9. Итоговая оценка

Проект стал устойчивее после пяти последних коммитов; прежний отчёт целиком переносить в текущий backlog уже нельзя. Существующие проверки проходят, но преимущественно подтверждают отдельные операции. Дополнительные сценарии показали проблемы на пересечении операций и во время отказов.

Практический порядок работы: **vault и согласованное сохранение → безопасные передачи → отмена и ошибки ресурсов → актуальность Git → политика clipboard → усиление IPC и проверка релиза**. Архитектуру можно развивать по этим этапам, сохраняя существующие границы main, preload, renderer и native.
