При `omit=peer` npm сохраняет исключённые зависимости в lock-файле, хотя не устанавливает их на диск: [документация npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/#omit). Поэтому наличие пакета в lock-файле не доказывает наличие его бинарников в сборке. HTML при этом перечисляет оба исключённых пакета, но не показывает пути обнаруженных 7-Zip. Причина расхождения пока не установлена: возможны особенности сканирования lock-файла, конфигурации установки или рабочего каталога сканера.

Локальный `npm audit --json --ignore-scripts` вернул 0, однако здесь установлен `offline=true`. Этот результат не считается свежей сетевой проверкой и не опровергает опубликованный advisory.

## 1. Зафиксировать воспроизводимую исходную проверку

Приоритет: первым этапом, до изменения зависимостей. Ответственный: сопровождающий сборки / CI.

- Получить перечисленные в HTML `grype_report.json`, `sbom.cyclonedx.json`, `audit_data.json`, отчёты OSV и журнал установки. В проекте найден только HTML.
- Для каждой группы 7-Zip сохранить фактический путь, версию, архитектуру, способ определения пакета и связь с npm-зависимостью. Низкую уверенность Grype не превращать автоматически в исключение.
- В отдельном чистом каталоге восстановить тот же commit вместе с `.npmrc`, зафиксировать версии Node/npm и эффективные `omit` / `include`, затем выполнить `npm ci --ignore-scripts --omit=peer`. Не переустанавливать рабочий `node_modules` ради сравнения.
- Построить SBOM фактической установки; отдельно сохранить анализ полного lock-файла. Повторить npm audit и OSV с актуальными базами и доступом к сети. Для сборки использовать Node 22, как в CI; локальный Node сейчас 24.14.1.

Готово, когда для каждой из 25 находок известны компонент, путь или запись lock-файла, источник и область присутствия: сборочная среда либо поставляемое приложение.

## 2. Исправить обе ветви minimatch

Приоритет: первая правка зависимостей. Ответственный: сопровождающий npm-зависимостей.

Затронутые цепочки:

- `electron-builder → app-builder-lib → @electron/universal → minimatch@9.0.9`.
- `electron-builder → app-builder-lib → minimatch@10.2.6`.
- `typescript-eslint → @typescript-eslint/typescript-estree → minimatch@10.2.6`.

Сначала проверить доступные обновления родительских пакетов. Если они ещё не переходят на исправленный minimatch, применить ограниченный override только для затронутых версий или родителей. Минимальная исправленная версия по [advisory сопровождающего](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249) — **11.0.1**; перед правкой проверить более свежие advisories и выбрать безопасную совместимую версию. Обновлять `package.json` вместе с lock-файлом средствами npm. Ветки 3.1.5 и 5.1.9 не входят в диапазон именно этой находки; глобальная замена всех major-версий не требуется.

Это переход между major-версиями, поэтому нужны проверки вызовов `Minimatch`, CommonJS/ESM и шаблонов упаковщика. У 11.0.1 заявлена поддержка Node `18 || 20 || >=22` и обоих способов импорта: [package.json версии 11.0.1](https://github.com/isaacs/minimatch/blob/v11.0.1/package.json). Совпадение engines не заменяет проверку поведения.

Условие атаки в advisory — управляемый атакующим glob-шаблон при `optimizationLevel >= 2`. В просмотренных вызовах упаковщика и `@electron/universal` этот параметр не задан, а в установленном minimatch по умолчанию равен 1. Это ограничивает подтверждённую достижимость; полный анализ всех вызовов не выполнен. Классификация — уязвимая зависимость инструментов сборки/анализа, эксплуатация через интерфейс TerminalDeck не подтверждена.

Готово, когда обе затронутые версии исчезли из lock-файла и установленного дерева, проверки проекта прошли, а упаковка Windows и macOS сохранила ожидаемый состав файлов.

## 3. Закрыть группу 7-Zip на основании артефактов

Приоритет: проверку вести одновременно с обновлением minimatch; обнаруженный используемый уязвимый бинарник исправлять до релиза. Ответственный: сопровождающий сборки.

- Сохранить действующее исключение ненужного Squirrel.Windows и добавить проверку, что после чистой установки `electron-builder-squirrel-windows` / `electron-winstaller` отсутствуют. Проверять файлы на диске, а не только поиск имён в lock-файле.
- Проверить Windows NSIS и portable, macOS dmg/zip и Linux-пакет, включая содержимое приложения, вложенные архивы и нативные ресурсы. Отдельно сканировать сборочную среду и инструменты из кэша упаковщика.
- Если старые 7-Zip отсутствуют, оформить для конкретных компонентов и CVE заключение «компонент отсутствует» с путями проверенных артефактов, их хэшами и датой. Не подавлять все CVE 7-Zip общим правилом.
- Если бинарник найден, определить поставляющий пакет или загружаемый инструмент, обновить его либо убрать неиспользуемый компонент и повторить сканирование. Не подменять файлы вручную внутри `node_modules`.

Готово, когда все 24 записи имеют подтверждённое решение: исправлено, компонент отсутствует либо сопоставление сканера опровергнуто конкретными доказательствами. Вывод из CHANGELOG 0.33.1 сам по себе недостаточен.

## 4. Уточнить отчёт и закрепить проверки в CI

Ответственный: сопровождающий CI. Выполнить после определения корректной исходной проверки.

- Выводить отдельно компоненты lock-файла, фактической установки и релизного пакета; сохранять версии сканеров и дату баз. Сбой сканера или недоступную базу показывать как неполную проверку.
- Проверять и dev-зависимости: Electron объявлен как devDependency, но его runtime поставляется пользователю. Сохранять npm audit и OSV; для бинарников — Grype/SBOM.
- Сохранять stdout/stderr и код завершения `npm audit signatures`; пустой вывод не считать успешной верификацией.
- Пересчитать lifecycle отдельно для реально исполняемых установочных скриптов, например `esbuild`, `ssh2`, `cpu-features`. Учесть, что [prepublishOnly запускается только при публикации](https://docs.npmjs.com/cli/v11/using-npm/scripts/#life-cycle-scripts). Если вводится ограничение скриптов, сначала проверить необходимые сборке действия.
- Добавить проверку отсутствия ненужного Squirrel.Windows после `npm ci` и сканирование собранных артефактов до публикации. Исключения делать адресными, с обоснованием и сроком пересмотра.

## Проверки перед завершением

После изменения зависимостей выполнить существующие `typecheck`, `lint`, `test`, `format:check`, `build`, `verify:release` и `verify:performance`; прогнать платформенные проверки Windows/macOS. Проверить упаковку установщика и portable, запуск приложения и основные SSH/RDP-сценарии. Нужны актуальные повторные сканы установки и релизных артефактов, а не только нулевой prod-аудит.

Оформить работы двумя изменениями: обновление зависимостей с доказательствами по 7-Zip; затем автоматизация проверок и улучшение отчёта. Релиз готов, когда обе ветви minimatch исправлены, все 24 записи 7-Zip разобраны, обязательные проверки прошли и итоговый отчёт содержит ссылки на доказательства. Срок упаковки и сканирования зависит от доступности исходных JSON, сетевых баз и платформенных сборок.
